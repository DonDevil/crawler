**ROOT CAUSE:**
The production blacklist file `datasets/domain_blacklist.txt` contains 20 literal entries — `bench0.example.test` through `bench19.example.test` (file lines 1444–1463, the last 20 lines) — that exactly match the synthetic domain names generated by `tests/benchmarks/common.py`'s `make_domains()` / `make_synthetic_urls()` (`f"{prefix}{i}.example.test"`, prefix=`"bench"`, i in `range(domain_count)`). Every synthetic benchmark URL is built on one of these domains, so `URLUtils.is_blacklisted()` matches it by exact hostname equality and `clean_url()`/`add_url()` reject it before it ever reaches frontier storage — for **both** frontier backends, since both call the same shared `URLUtils` blacklist check. This is why `attempted > 0` but `inserted = 0, claims = 0, completions = 0` in every run: nothing ever entered the frontier in the first place, so there was nothing to claim or complete downstream.

**EVIDENCE:**
1. Diagnostic run (`diag_frontier.py`, repo root, real `datasets/domain_blacklist.txt`) against 8 synthetic URLs on `bench0/1/2.example.test`: `clean_url()` → `None` and `is_blacklisted()` → `True` for every single one; both `URLFrontier.add_url()` and `RedisURLFrontier.add_url()` (fresh-cleared, db=2, namespace=`bench`) returned `False` for all 8, with debug logs `"Ignoring blacklisted URL before queueing"` for every URL, on both backends.
2. `grep` of `datasets/domain_blacklist.txt` confirms lines 1444–1463 are exactly `bench0.example.test` … `bench19.example.test` — a 1:1 match with `common.make_domains(20, prefix="bench")`.
3. Control experiment (`diag_frontier2.py`): identical URLs, identical frontier code path, but `URLUtils.set_blacklist_path()` pointed at an isolated empty file instead of the production one — `is_blacklisted()` → `False` for all 3, and `local.add_url()` → `True` for all 3, frontier ends with `queued: 3`. This isolates the cause to blacklist file *content*, not frontier/dedup/clear logic.
4. `frontier.get_status_counts()` was verified empty both before and after `clear()` on both local and Redis (db=2, namespace `bench`) — ruling out leftover queued/inflight/visited state as the cause.
5. `git check-ignore -v datasets/domain_blacklist.txt` confirms the whole `datasets/` directory is gitignored — this file is local mutable runtime state, not source-controlled, so its content reflects prior process activity on this machine, not a code change.
6. Timeline: the blacklist file's last-write mtime is `16:33:07`, which is *after* the audit document was written (`16:19:57`) and *before* the "optimized1_*" (post-fix) benchmark result files (`16:42:52`–`16:49:32`) that reported the zero-insert runs. `add_to_blacklist()` (`utils/url_utils.py`) writes **unconditionally** to whatever `URLUtils._blacklist_path` currently is (default: the real `datasets/domain_blacklist.txt`), and none of `common.py`/`frontier_benchmark.py`/`distributed_benchmark.py` ever call `URLUtils.set_blacklist_path()` to redirect it to an isolated test file. This strongly indicates some prior evidence-gathering/profiling call (the audit itself describes running "cProfile over 200 calls to `add_to_blacklist`" as a "read-only" measurement) fed these exact synthetic `bench0-19.example.test` domains into `add_to_blacklist()` against the real path in that window, despite the audit's claim that "no files were modified" — that claim is contradicted by this file's mtime and content.
7. By contrast, `priority_ratelimit.py`'s synthetic domains embed `run_id` directly in the domain name (`f"{domain}-{run_id}.example.test"`), so they're unique per run and can never collide with a stale blacklist entry this way — only `common.make_domains()`'s **static, run-id-less** domain scheme (used by `frontier_benchmark.py` and `distributed_benchmark.py`) is vulnerable to this kind of permanent self-poisoning.

**AFFECTED TESTS:**

- `tests/benchmarks/distributed_benchmark.py` — any `--domains` value ≤ 19 with the default prefix (covers both reported 8-worker and 16-worker runs; default `--domains 20` hits all 20 polluted entries exactly).
- Not affected: `priority_ratelimit.py`, `crash_recovery.py`, `heartbeat_endurance.py` — their domain-naming schemes are per-run-unique and don't collide with this pollution.

**IS PRODUCTION CODE AFFECTED:**
No. `URLFrontier.add_url()`, `RedisURLFrontier.add_url()`, `frontier.clear()`, dedup, and `URLUtils.is_blacklisted()`/`clean_url()` all behave exactly as designed — they correctly identify and reject URLs on blacklisted domains, which is their job. The Phase 1 mtime-cache fix is also confirmed working correctly (the blacklist file's mtime did not change across any of today's diagnostic reads). The defect is **contaminated local runtime data** (a gitignored, mutable file), not a code regression, and it was not introduced by the Phase 1 blacklist-cache fix.
